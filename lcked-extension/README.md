# LCKED — Browser Extension

A zero-knowledge password-manager extension that auto-fills, saves, and
updates logins in any web page. The extension talks to a Supabase backend
(via the PostgREST API — no SDK) and encrypts every vault entry locally
with **PBKDF2-SHA256 (600k iterations) + AES-256-GCM** before anything
leaves the device.

This is the companion extension for the [LCKED](..) Next.js web vault.

---

## Features

- 🔐 **Zero-knowledge crypto** — PBKDF2-SHA256 (600,000 iterations) derives a
  256-bit master key from your master password; AES-256-GCM encrypts every
  entry. The master password never leaves the browser.
- 🪄 **Smart auto-fill** — Detects login forms (password + username fields)
  on any page, including SPAs. Fills via native `input`/`change` events so it
  works with React, Vue, and Svelte.
- 📌 **Autofill badge** — A small mauve button appears at the corner of every
  detected password field. Click it to fill the best matching credential.
- 💾 **Save & update prompts** — When you submit a login (via `<form>` or a
  SPA button click), LCKED checks whether the password differs from the
  stored one and offers to **save** a new entry or **update** the existing one.
- 🌐 **Context menu** — Right-click anywhere on a page to access
  *LCKED: Auto-fill login* and *LCKED: Save/update this login*.
- ⌨️ **Keyboard shortcuts** — `Ctrl+Shift+L` opens the popup;
  `Ctrl+Shift+F` auto-fills the active tab.
- 🎨 **Mocha themed** — Catppuccin Mocha palette throughout (base `#1e1e2e`,
  mauve accent `#cba6f7`).
- 🧩 **MV3 service worker** — Background is an ES-module service worker that
  imports `lib/supabase.js` and `lib/crypto.js`. No bundler required.

## Installation

### 1. Load the unpacked extension

1. Open `chrome://extensions/`.
2. Enable **Developer mode** (top-right toggle).
3. Click **Load unpacked**.
4. Select the `lcked-extension/` directory.

The LCKED icon should appear in your toolbar. Pin it for quick access.

### 2. Set up the Supabase backend

The extension expects a single table named `vault_entries` with the
following columns:

```sql
create table vault_entries (
  id          uuid primary key default gen_random_uuid(),
  user_id     uuid not null,
  cipher      text not null,         -- base64 AES-256-GCM ciphertext
  iv          text not null,         -- base64 96-bit IV
  domain      text,                  -- plaintext hostname (for filtering)
  username    text,                  -- plaintext username (for matching)
  name        text,                  -- plaintext display name
  updated_at  timestamptz not null default now()
);

-- Enable Row-Level Security:
alter table vault_entries enable row level security;

create policy "users see their own rows"
  on vault_entries for select
  using (auth.uid() = user_id);

create policy "users insert their own rows"
  on vault_entries for insert
  with check (auth.uid() = user_id);

create policy "users update their own rows"
  on vault_entries for update
  using (auth.uid() = user_id)
  with check (auth.uid() = user_id);

create policy "users delete their own rows"
  on vault_entries for delete
  using (auth.uid() = user_id);
```

The extension also requires Email/Password auth to be enabled in your
Supabase project (Auth → Providers → Email).

### 3. Connect the extension

1. Click the LCKED toolbar icon.
2. In the popup, fill in:
   - **Supabase URL** — `https://<project-ref>.supabase.co`
   - **Anon / public key** — from *Project Settings → API → anon public*.
   - **Email** and **Password** — your Supabase auth user.
   - **Master password** — choose a strong password. This is used to derive
     the AES key; it is **never** sent to Supabase.
3. Click **Connect & unlock**.

The extension will:

1. Save the Supabase URL + anon key to `chrome.storage.local`.
2. Exchange email/password for a JWT via `/auth/v1/token` (stored locally).
3. Derive a 256-bit master key with PBKDF2-SHA256 (600k iterations) using a
   locally-generated 32-byte salt.
4. Store the raw key bytes in `chrome.storage.session` (in-memory only —
   cleared when the browser closes).
5. Fetch every `vault_entries` row, decrypt each one, and cache them in the
   service worker's memory.

From now on, opening the popup shows the **unlock** screen — enter your
master password to decrypt.

└────────────────┘         │                                           │
                           │  ┌─────────────┐  ┌────────────────────┐  │
                           │  │ in-memory   │  │ context-menu items │  │

                           │  └─────────────┘  └────────────────────┘  │
                           │           │                               │
                           │           ▼                               │
                           │  ┌─────────────┐  ┌────────────────────┐  │
                           │  │ lib/crypto  │  │ lib/supabase       │  │
                           │  │ PBKDF2+GCM  │  │ PostgREST client   │  │
                           │  └─────────────┘  └────────────────────┘  │
                           └──────────────┬────────────────────────────┘
                                          │ HTTPS (Bearer JWT)
                                          ▼
                                 ┌────────────────────┐
                                 │  Supabase          │

                                 └────────────────────┘

              ┌────────────────┐
              │  content.js    │  ◄── AUTOFILL / DETECT_SAVE / NOTIFY messages
              │  (per page)    │

                - autofill badge

### Message protocol

Messages flow over `chrome.runtime` between the popup, content script, and
background service worker. All messages are `{ type, ...payload }` and
respond with `{ ok: true, ... }` or `{ ok: false, error }`.

| Direction             | `type`                  | Payload                                        | Notes |
|-----------------------|-------------------------|------------------------------------------------|-------|
| popup → bg            | `GET_VAULT_STATUS`      | —                                              | returns `{configured, unlocked, itemCount, lastSyncedAt}` |
| popup → bg            | `UNLOCK`                | `{masterPassword}`                             | derives key, verifies, fetches + decrypts all rows |
| popup → bg            | `LOCK`                  | —                                              | clears session key + cache |
| popup → bg            | `GET_ITEMS_FOR_DOMAIN`  | `{domain}`                                     | returns matching decrypted items |
| popup → bg            | `GET_ALL_ITEMS`         | —                                              | returns all decrypted items |
| popup → bg            | `AUTOFILL_REQUEST`      | `{itemId}`                                     | sends `AUTOFILL` to active tab's content script |
| popup → bg            | `CHECK_UPDATE`          | `{domain, username, password}`                 | returns `{action: "update"\|"save_new"\|"noop", itemId?}` |
| popup → bg            | `SAVE_CREDENTIAL`       | `{id?, domain, name, username, password, urls?}` | encrypts + upserts row |
| popup → bg            | `DELETE_CREDENTIAL`     | `{id}`                                         | deletes row |
| popup → bg            | `REFRESH`               | —                                              | re-fetches + re-decrypts |
| popup → bg            | `LOGIN_EMAIL`           | `{email, password}`                            | Supabase `/auth/v1/token` (password grant) |
| popup → bg            | `CONFIGURE_SUPABASE`    | `{url, anonKey}`                               | saves to `chrome.storage.local` |
| popup → bg            | `LOGOUT_SUPABASE`       | —                                              | clears all config + session |
| popup → bg            | `RESET_VAULT`           | —                                              | clears salt + verifier + session |
| bg → content script   | `AUTOFILL`              | `{credentials}`                                | fills the best-matching form |
| bg → content script   | `DETECT_SAVE`           | —                                              | extracts visible credentials + shows save/update modal |
| bg → content script   | `NOTIFY`                | `{level, message}`                             | bottom-right toast |

### Domain matching

`domainMatches(stored, current)` returns `true` when:

- `stored === current` (after lowercasing and stripping a leading `www.`), or
- `current` ends with `"." + stored` (i.e. the current page is a subdomain
  of the stored domain — `login.example.com` matches a credential stored
  for `example.com`), or
- `stored` ends with `"." + current` (symmetric, for completeness).

This means a credential saved for `example.com` is offered on
`login.example.com`, `app.example.com`, etc. — but **not** on
`evilexample.com` (suffix-only match is rejected).

### Update vs. save_new detection

When the content script captures a credential after a submit, the
background runs `checkUpdate({domain, username, password})`:

- If a stored entry has the **same domain** + **same username** + **same
  password** → `action: "noop"` (no prompt).
- If a stored entry has the **same domain** + **same username** + a
  **different password** → `action: "update"` (with `itemId`) → the content
  script shows the **Update password?** modal.
- Otherwise (same domain, new username, or no match at all) →
  `action: "save_new"` → the content script shows the **Save login?** modal.

### Filling technique

The content script uses the native-value-setter trick to fill React/Vue
inputs:

```js
const setter = Object.getOwnPropertyDescriptor(
  HTMLInputElement.prototype, "value"
).set;
setter.call(el, value);
el.dispatchEvent(new Event("input",  { bubbles: true }));
el.dispatchEvent(new Event("change", { bubbles: true }));
el.dispatchEvent(new Event("blur",   { bubbles: true }));
```

This bypasses React's synthetic event system by setting the value through
the prototype's setter (React overrides the instance property to track
state) and dispatching native events that React's delegation layer picks up.

## Security model

### What the extension stores

| Storage                     | Keys                                   | Sensitive? | Lifetime |
|-----------------------------|----------------------------------------|------------|----------|
| `chrome.storage.local`      | `lcked_supabase_url`                   | no         | until sign-out / reset |
| `chrome.storage.local`      | `lcked_supabase_anon`                  | low        | until sign-out / reset |
| `chrome.storage.local`      | `lcked_supabase_token` (JWT)           | medium     | until sign-out / reset (or JWT expiry) |
| `chrome.storage.local`      | `lcked_supabase_uid`                   | low        | until sign-out / reset |
| `chrome.storage.local`      | `lcked_vault_salt` (32-byte PBKDF2 salt) | low      | until reset |
| `chrome.storage.local`      | `lcked_vault_verifier` (encrypted constant) | low   | until reset |
| `chrome.storage.session`    | `lcked_session_key` (raw AES key bytes) | **yes** | until lock / browser close |
| service worker memory       | `decryptedCache` (array of items)      | **yes**   | until lock / SW restart |

### What the extension never stores / never sends

- ❌ The master password (used once to derive the key, then dropped).
- ❌ Plaintext vault entries (only ever exist in the SW's memory while
  unlocked, and in the page after auto-fill).
- ❌ The raw session key is never sent over the network — it lives only in
  `chrome.storage.session`, which is **in-memory only** and cleared when
  the browser closes.

### Threat model & assumptions

- **Local-first**: even though entries are synced via Supabase, the
  encryption is end-to-end — Supabase only ever sees AES-GCM ciphertext.
  A compromised Supabase account cannot decrypt your vault.
- **Master password strength**: PBKDF2-SHA256 with 600,000 iterations
  provides ~30 bits of additional entropy vs. a single SHA-256 hash, but a
  weak master password can still be brute-forced offline if the server-side
  ciphertext leaks. Choose a long, unique passphrase.
- **Per-device salt**: the PBKDF2 salt is generated locally on first setup
  and is **not** synced via Supabase. This means installing the extension on
  a new device produces a different key — entries encrypted on device A
  cannot be decrypted on device B unless you export/import the salt (or
  re-set-up the vault). This is a deliberate trade-off for simplicity; a
  future version could store the salt as an encrypted blob in Supabase.
- **Auto-lock**: the vault stays unlocked for the lifetime of the browser
  session. Click the **Lock** button in the popup header to wipe the
  session key immediately. Closing the browser also wipes it.
- **Clipboard**: copying a password to the clipboard auto-clears after 20
  seconds to mitigate clipboard-sniffer attacks.

### Limitations

- The extension does not yet support TOTP, custom fields, notes, cards, or
  identities — only login items (name + username + password + domain).
- Cross-device salt sync is not implemented (see above).
- Auto-lock on tab visibility change is not wired in the extension (the
  Next.js web app has this; the extension uses the simpler session-store
  auto-clear).

## Development

This extension is plain JavaScript — no build step. Edit a file, then
click **Reload** on `chrome://extensions/` to pick up the changes.

To regenerate the icons:

```bash
cd lcked-extension/icons
python3 _gen.py
```

(Pillow is required: `pip install pillow`.)

To debug the service worker, click **Inspect views: service worker** on
the extension's card in `chrome://extensions/`. To debug the content
script, open DevTools on any page where LCKED is running and look for
the `lcked-ext-*` elements / `[LCKED bg]` console logs.

### Verifying the crypto

`lib/crypto.js` uses only the Web Crypto API (`crypto.subtle`):

- `deriveMasterKey` → `PBKDF2` with SHA-256, 600,000 iterations, 32-byte
  salt, deriving an `AES-GCM` 256-bit key (extractable, so it can be
  exported to `chrome.storage.session`).
- `encryptJson` → `AES-GCM` encrypt with a fresh 96-bit random IV per call.
- `decryptJson` → `AES-GCM` decrypt; GCM's authentication tag catches
  tampering or wrong-key attempts (throws on mismatch).
- `buildVerifier` / `verifyMasterKey` → encrypts the constant string
  `"lcked-verifier-v1"` with the derived key; future unlock attempts
  decrypt it to confirm the password is correct without keeping plaintext.
