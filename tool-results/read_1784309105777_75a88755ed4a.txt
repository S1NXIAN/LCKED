   106→Key Findings (high-signal summary):
   107→1. **100ms rule is non-negotiable** — every keystroke must paint in <100ms or the app is "keyboard-capable" not "keyboard-first" (Nielsen, UX Tigers). LCKED's decrypt-on-search must stay off the main thread.
   108→2. **LCKED's `⌘L` for lock collides with the browser URL bar** (every Chromium/Firefox). Should rebind to `⌘⇧L` (matches 1Password).
   109→3. **1Password's modifier-tiered copy pattern** (`⌘C` username / `⇧⌘C` password / `⌥⌘C` OTP) is the single highest-impact pattern LCKED is missing. Same verb, three tiers.
   110→4. **1Password's hold-`⌥` quasimode reveal** is safer than LCKED's toggle button — release to re-mask, can't be left on by accident.
   111→5. **Frecency + favorites (`⌘1`–`⌘9`)** beat LCKED's current fuzzy-only palette. Muscle-memory routes must be deterministic (Raycast's strict alias matching is the principle).
   112→6. **`?` context-aware cheat sheet** missing from LCKED — universal pattern (Superhuman/GitHub/Vimium/Notion).
   113→7. **Spatial arrow routing** between list (`↑↓`) and detail (`←→`) via roving tabindex — the 1Password signature; LCKED currently requires Tab.
   114→8. **Leader-key chords** (`g` then letter) for view/filter switching — Linear/GitHub/Vimium pattern, faster than `⌘K` for known destinations.
   115→9. **Selection-highlight slide via Framer Motion `layoutId`** — the Linear/Raycast signature micro-interaction that makes J/K feel physical. LCKED has AnimatePresence but not the sliding highlight.
   116→10. **Zero state-loss across lock/unlock** — LCKED must persist active item, scroll, search query, and unsaved editor drafts across lock. Critical for a password manager.
   117→11. **WCAG 2.1.4 compliance** — single-key shortcuts must be disable-able, remappable, and/or focus-scoped (always off in text inputs). LCKED should implement all three.
   118→12. **Native feel over web feel** (Raycast): no `cursor:pointer` on controls, no hover-everywhere, no flicker on transitions, popovers extend beyond bounds.
   119→13. **14 named principles** synthesised (100ms Rule, Spatial Consistency, Frecency over Recency, No Dead-Ends, Zero State-Loss, One Palette Mode Prefixes, Modifier-Tiered Verbs, Quasimodes over Toggles, Contextual Actions, Deterministic Muscle-Memory Routes, Native Feel, Power-User ≠ Inaccessible, Simple First Then Powerful, The Tool Disappears).
   120→14. **Ranked top-10 LCKED improvements** delivered (see brief §8), plus 10 honourable mentions.
   121→
   122→Deliverable: /home/z/RESEARCH-A-keyboard-UX-brief.md — full structured brief with binding tables for all 7 reference apps, named principles, 30+ cited URLs with 1-line descriptions, and the ranked top-10 improvements.

  1195→**1. Enable the React Compiler (Next.js 16 stable feature)**
  1196→- **Why LCKED:** LCKED already runs Next.js 16 + React 19 (`package.json`: `next ^16.1.1`, `react ^19.0.0`) but `next.config.ts` does NOT enable `reactCompiler`. The compiler automatically memoizes components and values, eliminating 90%+ of manual `useMemo`/`useCallback` boilerplate (per dev.to/Alex Bobes). LCKED has only 4 manual memoization sites (`item-list`, `totp-display`, `password-strength-meter`, `password-generator-dialog`) — the compiler would cover the other ~20 components for free.
  1197→- **How:** `bun add -D babel-plugin-react-compiler`, then add `reactCompiler: true` to `next.config.ts` (already Typed as `NextConfig`). Next 16's SWC wrapper only runs the compiler on files with JSX/Hooks, so build-time impact is minimal. Optional: start in `'annotation'` mode with `"use memo"` on hot components (`item-list`, `item-detail`) for safe rollout.
  1198→- **Expected impact:** 30–60% reduction in re-renders across the app. Improves **INP** on every interaction (search, filter, selection). Build cost: ~5–10% slower compiles (acceptable; Turbopack absorbs it).

  1200→**2. Move PBKDF2 (600k iterations) + bulk AES-GCM into a Web Worker**
  1201→- **Why LCKED:** `src/lib/crypto.ts` runs `deriveMasterKey` (PBKDF2-SHA256 @ 600k) and `encryptJson`/`decryptJson` (AES-256-GCM) **on the main thread**. PBKDF2 600k takes 200–500ms on mid-range hardware — during `unlock()` and `setupVault()` this freezes the entire UI. On unlock of a vault with 100+ items, the sequential decrypt-each-item loop (currently in `unlock`) blocks for seconds. BitAtlas's article confirms Web Crypto is fast per-op but the iteration count is brutal on the main thread. This is LCKED's single worst INP/TBT liability.
  1202→- **How:** Create `src/lib/crypto.worker.ts` using `comlink` (or a hand-rolled `postMessage` protocol). Move `deriveMasterKey`, `wrapVaultKey`, `unwrapVaultKey`, `buildVerifier`, `checkVerifier`, `encryptJson`, `decryptJson` into the worker. Main thread sends `{password, salt}` → worker returns `CryptoKey` (cannot be transferred across workers — but `ArrayBuffer` ciphertext CAN). For unlock: main thread posts `{wrappedVaultKey, iv, masterKey-derived-in-worker, items: StoredItem[]}` → worker decrypts all items in a batch and returns plaintext array. For save: post one `{plainItem, vaultKeyHandle}` → worker returns `{ciphertext, iv}`. Note: `CryptoKey` objects are not cloneable — keep keys inside the worker and pass opaque `keyId` handles back. Comlink makes this ergonomic.
  1203→- **Expected impact:** Eliminates the unlock-frame freeze. **INP** drops from 300–800ms → <50ms during decrypt. TBT on first unlock goes from seconds to near-zero. The single biggest perceived-perf win on this list.
  1204→
  1205→**3. Add `useDeferredValue` to search query in `item-list.tsx`**
  1206→- **Why LCKED:** `item-list.tsx:143-171` runs `searchItems(list, searchQuery)` synchronously inside `React.useMemo` keyed on `searchQuery`. The 3-strategy fuzzy matcher (substring + word-boundary + subsequence) is O(n·m) per keystroke. With 500+ items (a realistic power-user vault), every keystroke blocks the main thread → input lag > 100ms → violates the 100ms rule (Nielsen/UX Tigers, cited in RESEARCH-A). LCKED does NOT currently debounce or defer — the input feels "heavy" on big vaults.
  1207→- **How:** Wrap the search-query state with `const deferredQuery = React.useDeferredValue(searchQuery);` then key the `useMemo` on `deferredQuery` instead of `searchQuery`. The input stays responsive (React renders the input synchronously, defers the list re-filter). Add a subtle `<span>` opacity dim on the list while deferred to telegraph the work. Alternative: `useTransition()` + `startTransition(setSearchQuery)` — but `useDeferredValue` is one-line and doesn't require refactoring the setter.
  1208→- **Expected impact:** Search input stays <16ms per keystroke regardless of vault size. **INP** on typing drops from 50–200ms → <16ms on large vaults. No UX downside vs. debounce (no fixed delay).

  1210→**4. Add `content-visibility: auto` to off-screen list items and detail sections**
  1211→- **Why LCKED:** `item-list.tsx` renders ALL filtered items in a single `<ul>` with `<motion.li>` per row. With 200+ items, the browser must style/layout/paint every row even though only ~10 are visible. web.dev's benchmark shows `content-visibility: auto` gives a 7× initial-render boost on chunked content. Baseline Newly available Sept 2024 — safe to ship. LCKED's existing `motion.li` reflow on filter change is the worst-case scenario for this optimization.
  1212→- **How:** In `globals.css` add `*[data-item-id] { content-visibility: auto; contain-intrinsic-size: 0 56px; }` (56px = the row's measured height).   1213→- **Expected impact:** 5–7× faster initial list render on 100+ item vaults. **INP** on filter/sort changes drops dramatically (browser skips off-screen layout/paint). LCP unchanged (favicons still above-the-fold). Free win, zero runtime cost.

  1220→**6. Persist favicon cache to the Cache API / Service Worker**

  1230→**8. Batch Dexie writes during `unlock` migration + seed insertion**
  1231→- **Why LCKED:** `src/store/vault.ts` `unlock()` loops through items and calls `putStoredItem` (which calls `db.items.put`) one-by-one. The worklog says "batches re-encrypt + persist via `toReencrypt` queue" but the actual Dexie call is per-item. Dexie docs are explicit: `bulkPut()` is dramatically faster than a `put()` loop because it amortizes transaction overhead. RxDB's benchmark shows raw IndexedDB can take seconds for 300 sequential puts. Seed insertion of 15 items is small but a real Bitwarden import could be 300+.
  1232→- **How:** Replace `for (const item of toReencrypt) { await putStoredItem(...) }` with `await db.items.bulkPut(toReencrypt.map(item => ({ id, type, ciphertext, iv, createdAt, updatedAt })))`. Wrap the bulkPut in a single `db.transaction('rw', db.items, ...)` so it's atomic. Same for `importFromText` flow. Bonus: do the re-encryption itself in parallel via `Promise.all(toReencrypt.map(encryptJson))` — Web Crypto is concurrent.
  1233→- **Expected impact:** Unlock of a 300-item vault drops from ~3s → ~300ms. Import of a 500-item Bitwarden JSON drops from ~10s → ~1s. Improves **TBT** and perceived-perf during these one-shot operations.

  1239→**9. Add `subscribeWithSelector` middleware + `useStore.subscribe()` for the TOTP countdown ring**
  1240→- **Why LCKED:** `totp-display.tsx` updates every second (30s TOTP period with a circular countdown ring). Every `setState({ now: Date.now() })` re-renders the component. This is fine for one TOTP display, but if the detail panel ever shows multiple TOTP codes (it doesn't yet — but a "Reveal all" mode was mentioned in RESEARCH-A), or if the user navigates between TOTP items rapidly, the per-second re-render is wasteful. More importantly: the `Date.now()` state in `totp-display` is set on a `setInterval` — that's a React re-render every 1s for as long as the detail panel is open. TkDodo's transient-update pattern lets you mutate DOM directly without React.
  1241→- **How:** Add `subscribeWithSelector` to the Zustand `create` call. For the TOTP ring: instead of `useState + setInterval + setState`, use `useVault.subscribe(state => state.selectedId, selectedId => { ... })` to imperatively update a `ref`'s `style.strokeDashoffset` on each tick. This is the canonical "transient update" pattern from the Zustand docs. For now, the simpler win is: use `requestAnimationFrame` instead of `setInterval(1000)` and only update when the second-rollover changes (avoids the 1Hz React re-render entirely).
  1242→- **Expected impact:** Eliminates 1 React re-render per second while a TOTP item is open. Improves **INP** marginally on long sessions; bigger win is battery/CPU on mobile.

  1244→**10. Replace `motion.li layout` with `motion.li` + manual `layout` only when needed**
  1245→- **Why LCKED:** Every `<motion.li layout>` in `item-list.tsx:400-407` subscribes to Framer Motion's layout system. When the filter/sort changes, Framer records `getBoundingClientRect()` on EVERY item, diffs layouts, then animates. With 200 items, that's 200× layout reads + 200× writes per filter change — this is the textbook "layout thrashing" pattern Motion.dev's perf guide warns about. The animation itself is just opacity + y + scale (transform-only, GPU-accelerated) — but the `layout` prop forces the layout pass.
  1246→- **How:** Remove the `layout` prop from `<motion.li>` (keep `initial/animate/exit`). The list already has `AnimatePresence mode="sync"` so exit animations still work. The visual cost: items won't smoothly "slide" into their new positions when sorted — they'll fade-out-in-place then fade-in at the new position. For a password manager where the user sorts maybe once per session, that's a fine trade. Alternative: keep `layout` only on the active-row indicator (`layoutId="active-row"`) which is already isolated — it's the per-item `layout` that's expensive.

  1249→**11. Add `will-change: transform` (sparingly!) to the active-row indicator and Sheet**
  1250→- **Why LCKED:** The `motion.div layoutId="active-row"` (item-list.tsx:442-447) is the signature motion. Motion.dev's perf guide: "you can hint to the browser that they should create a new layer by setting `willChange: 'transform'`… do so sparingly." Same goes for the Sheet content (sliding in from the right) — it's a single transform animation that benefits from a dedicated layer.
  1251→- **How:** In `globals.css` add `.lcked-active-glow { will-change: transform; }` (it's `position: absolute; inset: 0` so it's already isolated). Critical: `will-change` is a hint, not free — each layer takes GPU memory. Never apply it broadly.

  1265→- **Why LCKED:** `unlock` does: derive master key (200–500ms) → unwrap vault key → check verifier → batch-decrypt all items → set state.   1274→**16. Migrate Dexie from `db.items.put` per save to a write-behind queue**
  1275→- **Why LCKED:** Every `saveItem`/`trashItem`/`restoreItem`/`moveItemToVault` does an immediate `putStoredItem` → `db.items.put`. That's one IndexedDB transaction per user action. With the optimistic UI, the user doesn't wait — but the transaction still burns a main-thread tick. For a "rapid edit" session (editing 5 fields on 3 items), that's 15 IDB transactions in quick succession.
  1276→- **How:** Use Dexie's `db.table.hook('creating', ...)` or a manual micro-batch: collect writes in a `Map<id, StoredItem>` and flush via `requestIdleCallback(() => db.items.bulkPut([...buffer.values()]))` with a 200ms max-delay cap. This is a "write-behind cache" pattern. Risk: if the tab closes before flush, the user loses their last edit. Mitigate with `navigator.locks` + `beforeunload` flush. Or simpler: only batch the optimistic `set()` calls, persist synchronously per-item as today — the real win is #8 (bulkPut on unlock/import) not on single-item edits.
  1277→- **Expected impact:** Marginal for single edits; meaningful for batch operations. **INP** on rapid multi-item actions (multi-select trash) drops. Lower priority than #8.

  1462→3. SLIDING SELECTION HIGHLIGHT — FULLY REWRITTEN (item-list.tsx):
  1463→   - Root cause of teleporting: the old approach used `{active && <motion.div layoutId="active-row" />}` inside each item. When the active item changed, the old motion.div unmounted and a new one mounted.
