    10→## TL;DR — The 5 Laws of Seamless Keyboard UX
    11→
    12→1. **100 ms or it's broken.** Every keystroke must produce visible feedback in under 100 ms or the app feels "keyboard-capable", not "keyboard-first" (Nielsen, UX Tigers).
    13→2. **One canvas, one caret, no dead-ends.** The keyboard user should never be stranded in a state where no key advances them. Every surface has an escape (`Esc`), a forward (`Enter`), and a search (`/` or `⌘K`).
    14→3. **Spatial consistency.** `J`/`K` always means down/up, `Enter` always means activate, `⌘K` always means command palette — everywhere in the app, no exceptions (Linear, Superhuman, GitHub, 1Password all agree).
    15→4. **Frecency + favorites over recency.** Surfaces that the user returns to (lists, palettes) should rank by *frequency × recency*, and let users pin a top-9 reachable via `⌘1`–`⌘9` (Raycast, 1Password, GitHub).
    16→5. **Power-user keyboard ≠ inaccessible.** Single-key shortcuts must be (a) disabled inside text inputs, (b) remappable, and (c) accompanied by ARIA live-region announcements of selection — otherwise WCAG 2.1.4 fails and screen-reader users are locked out (W3C, MDN).

    20→## 1. Keyboard-Driven App References — Patterns & Bindings
    21→
    22→### 1.1 Raycast — the gold standard
    23→Sources: [Raycast Manual — Aliases & Hotkeys](https://manual.raycast.com/command-aliases-and-hotkeys) · [A Technical Deep Dive Into the New Raycast](https://www.raycast.com/blog/a-technical-deep-dive-into-the-new-raycast) · [Destiner — Designing a Command Palette](https://destiner.io/blog/post/designing-a-command-palette)
    24→
    25→What makes it seamless:
    26→- **Two-tier shortcut model.** *Aliases* (short keyword typed into Root Search, strict prefix match, lowercased) for in-Raycast speed; *Hotkeys* (global, work even when Raycast is hidden) for system-wide instant access. Same command can have both.
    27→- **Hotkey types** include single-step (`⌥⌘A`), **double-tap modifier** (`⌘⌘`), and **single-key** (`fn` or `F13–F18`) — a power-user feature most web apps don't offer.
    28→- **Conflict detection at record time** with a visual recorder, auto-save countdown, and overwrite-with-warning. This is the pattern to copy.
    29→- **Favorites = `⌘1`–`⌘9`.** Up to 9 commands get number-key slots. This is the single highest-leverage "expert" feature a keyboard app can offer.
    30→- **Action panel inside commands.** `⌘K` inside any command opens a *nested* palette of actions on that item — "palettes in palettes" (Philip Davis).
    31→- **Native-feel discipline** (from the deep-dive): *no `cursor: pointer` on interactive controls* ("immediately signals 'this is a website'"), *no hover highlights on most controls* (desktop apps don't), *settings in a separate window not a modal*, *popovers render as native windows extending beyond bounds*, *no flicker on view transitions*.
    32→- **Strict alias matching** is a deliberate choice: "Aliases don't use fuzzy matching. They use strict prefix matching, which means they're always predictable. This makes them ideal for muscle-memory workflows." → **Principle: muscle-memory routes must be deterministic.**
    33→
    34→Concrete bindings to steal:
    35→| Binding | Action |
    36→|---|---|
    37→| `⌘K` (global) | Open Root Search |
    38→| `⌘1`–`⌘9` | Run favorited command N |
    39→| `⌘,` | Configure selected command |
    40→| `↵` | Run / select |
    41→| `⌘↵` | Run action as default |
    42→| `⌘⌫` | Delete / trash |

    44→### 1.2 Linear — keyboard-first project management
    45→Sources: [Linear Method — Introduction](https://linear.app/method/introduction) · [Descript's internal guide for using Linear](https://linear.app/blog/descript-internal-guide-for-using-linear) · [shortcuts.design — Linear](https://shortcuts.design/tools/toolspage-linear)
    46→
    47→What makes it seamless:
    48→- **Two-key chord navigation** with a leader key: `g` then letter (`gm` = My Issues, `gc` = Code, `gi` = Issues, `gp` = Projects). Mirrors Vim's `g`-prefix and is faster than any modifier combo.
    49→- **`o` then letter** for object navigation (`op` projects, `ot` teams, `od` docs).
    50→- **Single-key verbs** operate on the *active* item: `c` create, `a` assign, `l` label, `p` priority, `f` filter, `e` archive, `H` snooze, `Shift+H` unsnooze. This is the Linear signature — verbs are 1 key when an item is active.
    51→- **`⌘K` is contextual.** Same shortcut, but the menu shows commands *for the current item* (move to project, change status, add follower). Context-awareness is "where the super powers come from" (Sam Solomon).
    52→- **`j`/`k` everywhere** for list traversal, including the Inbox (treated like email).
    53→- Linear Method principles that apply directly to LCKED: **"Simple first, then powerful"**, **"Decide and move on"**, **"Say no to busy work"**, **"Build for the creators"** (i.e. optimise for the daily driver, not the occasional visitor).

    67→### 1.3 Superhuman — keyboard-driven email
    68→Sources: [Superhuman — Speed Up With Shortcuts](https://help.superhuman.com/hc/en-us/articles/46005789591693-Speed-Up-With-Shortcuts) · [Superhuman Cheat Sheet](https://pr33t.medium.com/superhuman-cheat-sheet-34087873513b) · [UseTheKeyboard — Superhuman](https://usethekeyboard.com/superhuman) · [KeyCombiner — Superhuman](https://keycombiner.com/collections/superhuman)
    69→
    70→What makes it seamless:
    71→- **`⌘K` is "Superhuman Command"** — a meta-palette: "As you type the action you want, …" → users don't memorise, they *search*.
    72→- **`?` reveals the cheat sheet** instantly, in-context (Flickr-style: changes per view).
    73→- **Single-key verbs on the inbox:** `e` archive, `s` star, `r` reply, `a` reply-all, `f` forward, `h` snooze, `x` select, `⏎` open.
    74→- **`j`/`k` traverse mail** — the universal list pattern.
    75→- **`G` then letter** jumps to folder (`Gi` Inbox, `Gs` Sent, `Gd` Done, etc.).
    76→- **`/` focuses search.**
    77→- **Multi-select via `Shift+↑/↓`** then bulk-act.
    78→- Philosophy: **the inbox is the home**, every verb is one key, and `⌘K` is the universal escape hatch when you don't remember a key.

    93→### 1.4 1Password 8 — desktop password manager (direct competitor reference)
    94→Source: [1Password Keyboard Shortcuts](https://support.1password.com/keyboard-shortcuts) (full table fetched)
    95→
    96→What makes it seamless — and note LCKED already mirrors several of these:
    97→- **Spatial arrow model.** `↑/↓` focus row in list; `→` focus right (detail) section; `←` focus left (list) section. This is the *roving tabindex* pattern made physical.
    98→- **Modifier-tiered copy.** `⌘C` = copy username, `⇧⌘C` = copy password, `⌥⌘C` = copy OTP. The *same verb* (`C`) at three modifier tiers — genius for a password manager.
    99→- **Quasimode reveal.** *Hold* `⌥` to temporarily reveal all secure fields — release to hide. A held-key quasimode (Raskin) — far safer than toggle.
   100→- **`⌘G` opens the password generator** — already in LCKED.
   101→- **`⌘\` autofill**, **`⇧⌘L` lock** — both global hotkeys.
   102→- **`⌘1`–`⌘9` switch accounts/collections** (1Password's version of favorites-as-numbers).
   103→- **Right-arrow = "view all available actions"** in Quick Access — a discoverable action menu per item.
   104→- **`⌘[`/`⌘]` back/forward** — spatial history navigation.
   105→- **`⌘F` search**, `Esc` clears.
   106→

   130→### 1.5 Vimium / Vimari / Tridactyl — browser vim bindings
   131→Sources: [KeyCombiner — Vimium](https://keycombiner.com/collections/vimium) · [Vim Tips Wiki — Vim key bindings for web browsers](https://vim.fandom.com/wiki/Vim_key_bindings_for_web_browsers) · [DevCtrl — Tridactyl & Surfingkeys](https://devctrl.blog/posts/tridactyl-surfingkeys-vimium-on-steroids)
   132→
   133→What makes them seamless:
   134→- **Hint mode (`f`)** is the killer pattern: pressing `f` overlays every clickable element with a 1–3 letter tag; typing the tag "clicks" that element. This is *keyboard-driven element targeting* — the web equivalent of `⌘K` for navigation.
   135→- **`hjkl` scrolling**, `gg`/`G` top/bottom, `d`/`u` half-page, `⌘F` full find.
   136→- **`/` find-in-page**, `n`/`N` next/prev match.
   137→- **`r`/`R`** reload/reload-hard, **`J`/`K`** next/prev tab.
   138→- **`?`** shows the cheat sheet, always.
   139→- **Mode discipline:** in text inputs, *all* single-key bindings are disabled automatically — the cardinal rule (also WCAG 2.1.4).
   140→
   141→The lesson for LCKED: a password manager doesn't need full vim, but the **hint-tag pattern** could inspire a "quick-jump" mode for power users with many items.
   142→
   143→### 1.6 Notion / Obsidian — slash commands & block editing
   144→Sources: [Notion — Keyboard Shortcuts](https://www.notion.com/help/keyboard-shortcuts) · [Vida.io — Notion Shortcuts](https://vida.io/blog/notion-shortcuts) · [Obsidian Forum — Slash Commands](https://forum.obsidian.md/t/slash-commands-and-quick-format/61738)
   145→
   146→What makes them seamless:
   147→- **`/` slash commands** trigger an *inline* block-insertion menu at the caret — not a modal. "Prioritized display of commonly used formatting commands, with keyboard accessibility" (Obsidian forum).
   148→- **`⌘/`** opens a command palette on the selected block.
   149→- **`[[`** opens a page-link picker, **`@`** opens a mention picker — *typed triggers* that double as syntax.
   150→- **`⌘⇧↑/↓`** move the current block up/down.
   151→- **`Enter`** new block, **`Shift+Enter`** soft line break, **`Esc`** exit block.
   152→- Obsidian: **fully customisable hotkeys** + a `⌘P` command palette (VS Code-style).
   153→
   154→The lesson: typed triggers (`/`, `[[`, `@`) are *zero-modifier* shortcuts that work because they're unambiguous inside an editor. LCKED could use `/` in a search box to mean "filter by type" (e.g. `/login`, `/card`).
   155→
   156→### 1.7 GitHub — command palette at scale
   157→Sources: [GitHub Command Palette](https://docs.github.com/en/get-started/accessibility/github-command-palette) · [GitHub Keyboard Shortcuts](https://docs.github.com/en/get-started/accessibility/keyboard-shortcuts) · [KeyCombiner — GitHub](https://keycombiner.com/collections/github)
   158→
   159→What makes it seamless:
   160→- **Two palette modes** behind different shortcuts: `⌘K` (or `Ctrl+K`) = *search* mode; `⌘⇧K` = *command* mode. Same UI, different intent. This is the cleanest answer to "search vs command" (Solomon's trap).
   161→- **`?` context-aware cheat sheet** — different on every page.
   162→- **`g` then letter** for section nav (`gc` Code, `gi` Issues, `gp` Pulls, `gn` Notifications).
   163→- **`/`** focuses the page search.
   164→- **`t`** file finder, **`l`** label, **`c`** comment, **`a`** assignee, **`r`** reviewer, **`s`/`w`** subscribe/unsubscribe.
   165→- **Prefix syntax in palette:** `>`, `#`, `@`, `!` switch between command/issue/user/repo scopes — a single palette, many modes (Sublime's `@`/`:` idea, refined).
   166→
   167→Lesson: **one palette, mode prefixes** scales better than many palettes.
   168→
   169→### 1.8 Shared patterns across all seven apps
   170→1. `⌘K` opens the command palette (web de-facto standard). `Ctrl+K` on Windows/Linux.
   171→2. `j`/`k` (or `↑`/`↓`) traverse lists. Always.
   172→3. `?` reveals a context-aware cheat sheet.
   173→4. `/` focuses search.
   174→5. `Esc` closes the topmost surface and returns focus.
   175→6. `Enter` activates; `⌘Enter` submits/commits the primary action.
   176→7. Leader-key chords (`g` + letter, `o` + letter) for navigation — no modifier needed.
   177→8. `⌘1`–`⌘9` for favorites / sections / accounts.
   178→9. Single-key verbs operate on the *active* item only — disabled in text inputs.
   179→10. The palette is *contextual* — it shows actions relevant to what's focused.

   183→## 2. Command Palette Best Practices
   184→
   185→Sources: [UX Patterns — Command Palette](https://uxpatterns.dev/patterns/advanced/command-palette) · [Sam Solomon — Designing Command Palettes](https://solomon.io/designing-command-palettes) · [Destiner — Designing a Command Palette](https://destiner.io/blog/post/designing-a-command-palette) · [Philip Davis — Command Palette Interfaces](https://philipcdavis.com/writing/command-palette-interfaces) · [Avery Vigolo — Good design patterns: the command palette](https://averyv.me/blog/command-palette) · [kbar (GitHub)](https://github.com/timc1/kbar) · [cmdk / react-cmdk](https://react-cmdk.com)
   186→
   187→### 2.1 Anatomy (UX Patterns)
   188→Required parts: **Trigger** (hotkey or button) → **Search input** (focus anchored here) → **Grouped results** (commands / pages / recent) → **Result item** (label + hint text + shortcut). Optional but essential: **Empty state**, **Loading state**, **Error state**.
   189→
   190→### 2.2 When to use — and when not to
   191→- **Use** when the product has many destinations + power-user commands and a stable expert workflow (UX Patterns).
   192→- **Don't use** if the surface is small (use a visible nav menu instead) or if the team can't support the state complexity (loading/empty/error/focus) — "the biggest risk is not the default visual state, it's the combination of state management, accessibility, and recovery behavior once loading, errors, or narrow screens enter the picture" (UX Patterns FAQ).
   193→- **Don't conflate search and command palette.** If search is core, place it *beside* the palette (Salesloft). If search is secondary, make it a command *inside* the palette (Solomon).
   194→
   195→### 2.3 Variations
   196→- **Universal launcher** — mixes nav, creation, settings (Raycast, GitHub, Linear). Best for action-heavy apps.
   197→- **Contextual palette** — only actions for the current object (Linear's `⌘K` on an issue, Notion's `⌘/` on a block).
   198→- **Recent-first palette** — promotes recent commands and workspaces before search matches. "Use when repeat use and speed matter more than exhaustive discovery" (UX Patterns).
   199→
   200→### 2.4 Ranking — frecency over recency
   201→- **Frecency** = frequency × recency. The dominant pattern in Raycast, Linear, Spotlight, Alfred, VS Code Quick Open. Items you use often *and* recently rise to the top.
   202→- **Favorites beat frecency.** Pinned items (`⌘1`–`⌘9`) must always win (Raycast).
   203→- **Caveat (Avery Vigolo):** pure frequency-ranking can break muscle memory if two similar items jockey for #1. Solution: **deterministic tiebreakers** (exact alias match > prefix > fuzzy; shown-text match > hidden-text; word-boundary > substring) and an *opt-out* for users who "rely on learning the bare minimum they need to type."
   204→- **Sort heuristics (Vigolo):** (1) matched shown-text first, (2) prefix match > substring, (3) whole-word > partial-word.
   205→
   206→### 2.5 Action vs navigation items
   207→Two kinds of items in a palette: **navigations** (go to X) and **actions** (do Y). Solomon's rule: *command palettes are for doing, not just finding*. A palette that only navigates is a search box with extra steps.
   208→
   209→### 2.6 Nested actions & handoffs
   210→- VS Code does rename *inline* in the palette. Obsidian closes the palette and focuses the document's Name field. "I don't know that there is a right answer… but pulling more interactions into the palette will increase complexity a good deal" (Solomon).
   211→- **Raycast "palettes in palettes"** — extensions are mini-apps inside the palette with their own forms, lists, markdown (Philip Davis, Destiner).
   212→- **Rule of thumb:** pull an interaction into the palette if it's <2 fields; if more, close the palette and focus a form (Solomon's handoff principle).
   213→
   214→### 2.7 Required features (Destiner's checklist)
   215→1. List *all* menu + context-menu actions (not a subset — Sublime's flaw).
   216→2. Show hotkeys next to each command (waste of "electronic real estate" not to).
   217→3. Conventional hotkey: `⌘K` (web) or `⌘/`. Don't fight the standard.
   218→4. Fuzzy search (Raycast lags here — exact substring only — which is a known weakness).
   219→5. Favorites (`⌘1`–`⌘9`).
   220→6. Discoverability on launch: recent, frequent, suggested commands. "A good palette guides the user through its capabilities."
   221→7. Single entry point — avoid Sublime's "Go To File / Go To Line / Go To Symbol" menu sprawl; use **prefixes** (`@`, `:`, `#`) instead.
   222→8. Togglable — re-pressing the hotkey dismisses.
   223→9. Optional: multi-level palette (Raycast extensions, GitHub org/repo drill-down).
   224→10. Optional: built-in search inline (GitHub) or via `?` prefix (Destiner).
   225→
   226→### 2.8 Implementation libraries
   227→- **cmdk** (by Pacocoursey, used by Vercel, Linear) — primitives, fuzzy search built in, headless. The de-facto choice for Next.js/shadcn apps (shadcn/ui ships a `Command` component built on cmdk).
   228→- **kbar** — "fast, portable, extensible… plug-n-play" with built-in focus management, keyboard nav, async commands, global prefix modes. Heavier than cmdk but more batteries-included.
   229→- **Headless UI Combobox** — alternative if you're already on Tailwind + Headless UI.
   230→
   231→For LCKED: **cmdk (via shadcn/ui `<Command>`) is the correct choice** — already aligned with the stack.

   235→## 3. Keyboard Shortcut Taxonomy & Conventions
   236→
   237→Sources: [Sasha Maximova — J, K, or How to choose keyboard shortcuts](https://sashika.medium.com/j-k-or-how-to-choose-keyboard-shortcuts-for-web-applications-a7c3b7b408ee) · [Mathias Polligkeit — Two Common Pitfalls](https://www.mathiaspolligkeit.com/two-common-pitfalls-for-keyboard-shortcuts-in-web-applications) · [WCAG 2.1.4 Character Key Shortcuts](https://www.w3.org/WAI/WCAG22/Understanding/character-key-shortcuts.html) · [MDN — aria-keyshortcuts](https://developer.mozilla.org/en-US/docs/Web/Accessibility/ARIA/Reference/Attributes/aria-keyshortcuts)
   238→
   239→### 3.1 The web-standard convention table
   240→| Binding | Meaning | Used by |
   241→|---|---|---|
   242→| `⌘K` / `Ctrl+K` | Open command palette | Linear, GitHub, Raycast, Superhuman, Vercel, Notion, Slack |
   243→| `⌘/` | Show shortcuts / alt palette open | 1Password, Notion, macOS Help |
   244→| `⌘N` | New (item/window) — **caution: conflicts with browser New Tab** | 1Password (app), Linear |
   245→| `⌘F` | Find / search | universal |
   246→| `⌘E` | Edit (1Password) — caution: macOS "Use Selection for Find" | 1Password |
   247→| `⌘G` | Generator (1Password) / Find next (browser) | 1Password |
   248→| `⌘L` | Lock (1Password) / focus URL bar (browser) — **conflict!** | LCKED uses `⌘L` for lock |
   249→| `⌘1`–`⌘9` | Switch section / favorite | 1Password, Raycast, browsers (tabs) |
   250→| `j` / `k` | Next / previous item (when not in input) | Vimium, Linear, Superhuman, GitHub |
   251→| `↑` / `↓` | Next / previous (alt to j/k) | 1Password, Notion |
   252→| `g` + letter | Go to section (leader key) | Linear, GitHub, Vimium |
   253→| `?` | Show cheat sheet | Superhuman, GitHub, Vimium, Notion |
   254→| `/` | Focus search (outside inputs) | GitHub, Vimium, Superhuman |
   255→| `Esc` | Close / cancel / clear | universal |
   256→| `Enter` | Activate / open | universal |
   257→| `⌘Enter` | Submit / primary action | universal |
   258→
   259→### 3.2 Single-key vs modifier — the rule
   260→- **Modifier shortcuts (`⌘`, `Ctrl`, `⌥`, `⇧` + key)** are safe inside text inputs and don't conflict with typing. Use for *global / app-level* actions.
   261→- **Single-key shortcuts** (`j`, `k`, `c`, `e`, `?`, `/`) are faster and more memorable but *must* be disabled when a text input, textarea, or contenteditable has focus (Vimium, Linear, Superhuman all do this).
   262→- **WCAG 2.1.4 (Level A)** requires that if you implement single-character shortcuts, you must provide a way to (a) turn them off, (b) remap them, or (c) only activate them on focus. **Non-negotiable for LCKED.**
   263→
   264→### 3.3 Two pitfalls to avoid (Polligkeit)
   265→1. **Never use `Alt`/`Option` + character.** International layouts own those combos:
   266→   - German QWERTZ: `@` = `Alt+Q`
   267→   - French AZERTY: `é` = `Alt+2`, `/` = `Alt+K`
   268→   - German Neo2: every `Alt+letter` is a programming symbol
   269→   - **Use `Ctrl` or `Ctrl+Shift` instead.** `Meta` (⌘) on Mac is generally safe but watch system shortcuts.
   270→2. **Use `event.key`, not `event.code`.** `event.code` is physical-key-position (breaks on AZERTY/QWERTZ); `event.key` is the produced character (matches user expectation). Avoid deprecated `keyCode`, `charCode`, `which`.
   271→
   272→### 3.4 Discoverability — surfacing shortcuts
   273→- **`?` cheat sheet**, context-aware (Flickr, GitHub, Superhuman).
   274→- **Show the shortcut inline** in menu items, tooltips, dialog buttons, and *next to every command-palette entry* (Destiner: "a waste of electronic real estate not to").
   275→- **Status-bar hints** (Confluence, Checkvist) — show the 2–3 most relevant shortcuts for the current view in a footer.
   276→- **First-run hint overlay** (Linear, Notion) — one-time onboarding that points at `⌘K`.
   277→- **Nudge pattern** (somus/linear-shortcut-nudger) — subtly suggest the shortcut when a user does the mouse equivalent 3× in a row.
   278→
   279→### 3.5 Avoiding collisions
   280→- Don't override browser/OS shortcuts: `⌘N`, `⌘O`, `⌘S`, `⌘P`, `⌘W`, `⌘T`, `⌘L` (URL bar!), `⌘F`, `⌘C/V/X/A/Z/Y` (Maximova). LCKED's `⌘L` for lock **does collide** with the browser URL bar — consider `⌘⇧L` (matches 1Password) or `⌘Esc`.
   281→- GitHub's `Ctrl+K` collides with Firefox's search bar — they offer customisable alternatives in Settings (GitHub Discussion #15255). **Allow customisation.**
   282→- ⌘K inside Markdown editors already means "insert link" (GitHub). Use `⌘⇧K` for command mode (GitHub's solution).

   286→## 4. Focus Management & Spatial Navigation
   287→
   288→Sources: [W3C APG — Developing a Keyboard Interface](https://www.w3.org/WAI/ARIA/apg/practices/keyboard-interface) · [MDN — Keyboard-navigable JS widgets](https://developer.mozilla.org/en-US/docs/Web/Accessibility/Guides/Keyboard-navigable_JavaScript_widgets) · [Adobe Spectrum — Roving Tab Index](https://opensource.adobe.com/spectrum-web-components/tools/roving-tab-index) · [Open UI — Focusgroup Explainer](https://open-ui.org/components/scoped-focusgroup.explainer) · [Orange — Listbox and keyboard navigation](https://a11y-guidelines.orange.com/en/articles/listbox-and-keyboard-navigation) · [W3C APG — Dialog (Modal)](https://www.w3.org/WAI/ARIA/apg/patterns/dialog-modal) · [UXPin — Restore Focus After Modal Dialogs](https://www.uxpin.com/studio/blog/restore-focus-after-modal-dialogs) · [TestParty — Modal Dialog Accessibility](https://testparty.ai/blog/modal-dialog-accessibility)
   289→
   290→### 4.1 Roving tabindex (the composite-widget pattern)
   291→- One element in the composite has `tabindex="0"` (the active one); all others have `tabindex="-1"`. Tab enters the composite at the active item; arrow keys move the `0` between items.
   292→- Tabbing away and back *remembers your place* — crucial for list+detail layouts.
   293→- **Native alternative:** the `focusgroup` HTML attribute (Chrome/Edge) implements roving tabindex declaratively: `<div focusgroup>…<button>…</button>…</div>`. Not yet cross-browser, but the future.
   294→
   295→### 4.2 Listbox keyboard model (WAI APG)
   296→- List container is focusable (`tabindex="0"` when empty, roving otherwise).
   297→- `↑`/`↓` move selection (and focus, in "auto" selection model).
   298→- `Home`/`End` jump to first/last.
   299→- Type-ahead: printable chars move to next item starting with that substring.
   300→- `Enter` activates; `Esc` (in combobox) closes.
   301→- **Focus vs selection** can be decoupled (Visual Studio style) but for password-manager lists, *focus follows selection* (auto) is the right default.
   302→
   303→### 4.3 Arrow-key spatial model for master/detail (1Password-style)
   304→- `↑/↓` move in the list (left pane).
   305→- `→` moves focus to the detail pane (right).
   306→- `←` moves back to the list.
   307→- Inside the detail pane, `Tab` cycles fields; `⌘C`/`⇧⌘C`/`⌥⌘C` copy.
   308→- This is roving tabindex *between* composites, with arrow keys as the spatial router.
   309→
   310→### 4.4 Modal focus management (WAI Dialog APG, TestParty)
   311→Required behaviour, in order:
   312→1. **Capture the trigger.** Store a ref to the element that opened the dialog *before* transferring focus.
   313→2. **Move focus into the dialog** on open — first focusable, or the primary action, or the dialog container itself (`tabindex="-1"`).
   314→3. **Trap focus** — Tab cycles within the dialog; Shift+Tab at the first wraps to the last.
   315→4. **Esc closes** and returns focus to the trigger.
   316→5. **Restore focus** to the trigger on close (or to a logical successor if the trigger was removed).
   317→6. Use `aria-modal="true"` and `role="dialog"` (or `<dialog>` element, which does 1–5 natively in modern browsers).
   318→7. **Inert the background** (`inert` attribute or `aria-hidden` on siblings) so screen readers can't wander.
   319→
   320→For LCKED: shadcn/ui's `Dialog`/`AlertDialog` already implement 1–7 via Radix. Verify focus-restore *to the specific button* (not just the list) — a common Radix gotcha.
   321→
   322→### 4.5 Focus rings (WCAG 2.4.7 + 2.4.13)
   323→- **Never** `outline: none` without a replacement (78% of homepages fail this — WebAIM 2024).
   324→- Use `:focus-visible` to show rings only for keyboard users (not mouse clickers).
   325→- Ring spec (WCAG 2.4.13 Focus Appearance, AAA): **≥2 CSS px thick**, **≥3:1 contrast** against both the element and adjacent background, **not obscured**.
   326→- **Double-ring pattern** for any-background safety: `outline: 2px solid #fff; outline-offset: 2px; box-shadow: 0 0 0 4px #000;`.
   327→- shadcn/ui's `ring-2 ring-ring` is compliant if `--ring` token has ≥3:1 contrast.
   328→
   329→### 4.6 scroll-into-view
   330→- Every focused/selected list item must call `el.scrollIntoView({ block: "nearest" })` so arrow navigation never leaves the active item off-screen. cmdk does this by default; verify in custom lists.

   334→## 5. Micro-Interactions & Motion for Keyboard UIs
   335→
   336→Sources: [Motion.dev — Layout Animation](https://motion.dev/docs/react-layout-animations) · [Maxime Heckel — Everything about Framer Motion layout animations](https://blog.maximeheckel.com/posts/framer-motion-layout-animations) · [Motion.dev — React transitions](https://motion.dev/docs/react-transitions) · [Theodorus Clarence — List Animation using Motion for React](https://theodorusclarence.com/blog/list-animation) · [Tatiana Mac — prefers-reduced-motion](https://www.tatianamac.com/posts/prefers-reduced-motion) · [Motion.dev — Accessibility](https://motion.dev/docs/react-accessibility)
   337→
   338→### 5.1 The selection-highlight slide (the Linear/Raycast signature)
   339→- Use Framer Motion's **`layoutId`** to render a single `<motion.div layoutId="list-active-bg" />` as the active row's background. When the active index changes, Framer animates the highlight sliding from one row to the next — *no manual transitions*.
   340→- Wrap the list in `<LayoutGroup>` to namespace the `layoutId` (Maxime Heckel).
   341→- This is the single highest-impact micro-interaction for a keyboard UI: it makes `j`/`k` feel *physical*.
   342→
   343→### 5.2 Modal spring
   344→- Modal open: `initial={{ opacity: 0, scale: 0.96, y: 8 }}` → `animate={{ opacity: 1, scale: 1, y: 0 }}` with `transition={{ type: "spring", stiffness: 300, damping: 26 }}`.
   345→- Overlay: `initial={{ opacity: 0 }}` → `animate={{ opacity: 1 }}`, `duration: 0.15`.
   346→- Exit must mirror (via `AnimatePresence`).
   347→- **Critical:** spring duration must be <200ms to avoid feeling sluggish under rapid `⌘K` open/close (Raycast "no flickering on view transitions").
   348→
   349→### 5.3 List item enter/exit stagger
   350→- Use `AnimatePresence` + per-item `initial`/`animate`/`exit` with a small stagger (`delay: index * 0.02`, capped at 5 items).
   351→- **Cap stagger total at ~150ms** — beyond that it feels like the app is loading, not animating.
   352→
   353→### 5.4 Performance budgets
   354→- **Animation budget: 16ms/frame (60fps).** Layout animations (`layout`, `layoutId`) are GPU-composited transforms — safe. Avoid animating `width`/`height`/`top`/`left` directly.
   355→- **Raycast's lesson:** even one frame of blank content breaks the illusion — pre-render expanded states, keep WebView frame at max size, sync with `requestAnimationFrame` before showing. For web: avoid layout thrash from `clientWidth` reads mid-animation.
   356→- **Input latency budget: 100ms.** (Nielsen.) Every keystroke → painted character in <100ms or the keyboard feels broken. For LCKED's local-first crypto: decrypt-on-search must be off the main thread or pre-decrypted, never blocking keystrokes.
   357→
   358→### 5.5 Reduced motion (Tatiana Mac — no-motion-first)
   359→- **Mindset:** "Is this animation critical to understanding the content?" If no (usually), default to `animation: none` and only *add* animation for `@media (prefers-reduced-motion: no-preference)`.
   360→- Framer Motion (now `motion`) automatically disables transform/layout animations when the user has Reduce Motion on (Motion.dev docs). Verify with `useReducedMotion()` hook for custom transitions.
   361→- **Replace, don't remove:** for reduced motion, swap a slide for an instant opacity cut, not a frozen intermediate state.
   362→- Vestibular disorders (BPPV) are real — scroll-jacking, parallax, and large-scale motion can cause physical illness. LCKED should never scroll-jack.
   363→
   364→### 5.6 Hover discipline (from Raycast deep-dive)
   365→- Web hover highlights on *every* interactive control "immediately signal 'this is a website'" to desktop users. For a keyboard-first app, **reserve hover for actual mouse users** and don't rely on it for affordance — the keyboard active state (`[data-active]` or `aria-selected`) is the primary signal.

   369→## 6. Accessibility Interplay — Power-User Keyboard + Screen Reader
   370→
   371→Sources: [MDN — ARIA Live Regions](https://developer.mozilla.org/en-US/docs/Web/Accessibility/ARIA/Guides/Live_regions) · [Sara Soueidan — Accessible notifications with ARIA Live Regions](https://www.sarasoueidan.com/blog/accessible-notifications-with-aria-live-regions-part-1) · [a11y-collective — Complete Guide to ARIA Live Regions](https://www.a11y-collective.com/blog/aria-live) · [Vispero — Screen reader support for ARIA live regions](https://vispero.com/resources/screen-reader-support-aria-live-regions) · [W3C APG — Combobox](https://www.w3.org/WAI/ARIA/apg/patterns/combobox) · [WCAG 2.1.4](https://www.w3.org/WAI/WCAG22/Understanding/character-key-shortcuts.html)
   372→
   373→### 6.1 The tension
   374→Power-user keyboards use single-key shortcuts (`j`/`k`/`c`/`e`) which (a) conflict with screen-reader quick-nav keys and (b) violate WCAG 2.1.4 unless remappable. The goal: **make the same UI work for both**.
   375→
   376→### 6.2 ARIA live regions for selection
   377→- As `j`/`k` moves the active item, announce it: a `role="status"` (polite) region that updates to "Selected: GitHub, login, 2 of 47".
   378→- Use `aria-atomic="true"` if you want the full string re-announced, `false` (default) for diff-only.
   379→- **Polite** for selection/count changes; **assertive** only for errors and clipboard-copied confirmations.
   380→- Most-supported combo (Vispero): `aria-live="assertive"` + `role="status"` — but `polite` is usually right for selection.
   381→
   382→### 6.3 Pattern: command palette as combobox
   383→- The WAI Combobox pattern is the correct ARIA model for a command palette: input has `role="combobox"` + `aria-expanded`; results list has `role="listbox"`; items have `role="option"` + `aria-selected`.
   384→- `aria-activedescendant` on the input tracks the active option *without moving DOM focus* — this is what lets `j`/`k` work without breaking the input. **cmdk does this by default.**
   385→- Announce result count: "47 results, 1 selected" via live region.
   386→
   387→### 6.4 Single-key shortcut WCAG compliance (2.1.4)
   388→Three compliance paths (any one suffices):
   389→1. **Turn off** — user can disable all single-key shortcuts.
   390→2. **Remap** — user can rebind to modifier shortcuts.
   391→3. **Active only on focus** — shortcuts fire only when the relevant composite has focus (and never when a text input has focus).
   392→For LCKED: implement (1) + (2) + (3) — they're cheap and the combo is the gold standard. 1Password, Linear, and GitHub all do (3) implicitly; GitHub also does (1)+(2).
   393→
   394→### 6.5 aria-keyshortcuts
   395→- Annotate every shortcut-bearing element: `<button aria-keyshortcuts="Meta+K">`. Screen readers can then announce "available shortcut ⌘K".
   396→- Format per MDN: modifier names are `Alt`, `Control`, `Shift`, `Meta`; keys are literal (`K`, `1`, `Enter`); join with `+`.
   397→
   398→### 6.6 Screen-reader cheat sheet parity
   399→- The `?` cheat sheet must be a real focusable dialog (not just a visual overlay) so screen-reader users can browse shortcuts too.

   403→## 7. "Seamless" UX Principles — What Separates Seamless from Capable
   404→
   405→Sources: [Nielsen — Response Time Limits](https://www.nngroup.com/articles/response-times-3-important-limits) · [UX Tigers — Time Scales of UX](https://www.uxtigers.com/post/time-scales-ux) · [Linear Method](https://linear.app/method/introduction) · [Raycast Technical Deep Dive](https://www.raycast.com/blog/a-technical-deep-dive-into-the-new-raycast) · [UX Patterns — Command Palette](https://uxpatterns.dev/patterns/advanced/command-palette) · [Simon Hearne — Optimistic UI Patterns](https://simonhearne.com/2021/optimistic-ui-patterns) · [UX Planet — Optimistic UIs](https://uxplanet.org/optimistic-ui-34d9eefe4c05)
   406→
   407→### 7.1 Named principles
   408→1. **100 ms or instantaneous (Nielsen).** Below 100 ms, the user perceives the *cause* (their keypress) as directly producing the *effect*. Above 100 ms, the computer becomes the agent. For a keyboard app, **every keypress must paint in <100 ms**.
   409→2. **1 s or in-flow (Nielsen).** Below 1 s, the user stays in a "seamless flow of thought" — they "feel in control of the overall experience and work freely." Above 1 s, flow breaks.
   410→3. **10 s or attention-lost (Nielsen).** Above 10 s, short-term memory drains and the user must reorient. Provide progress feedback for anything >1 s.
   411→4. **No dead-ends.** Every surface has an `Esc`, an `Enter`, and a way forward. Linear's `g`-then-letter has a visible leader-key hint so the user is never stuck mid-chord.
   412→5. **Zero state-loss.** Modal open/close, palette open/close, lock/unlock must *never* lose the user's place (scroll position, active item, unsaved draft). "Persist enough context that users can leave and return without feeling like the system forgot their progress or place" (UX Patterns). LCKED must restore active item + scroll + search query after unlock.
   413→6. **Spatial consistency.** `j`/`k` mean down/up *everywhere*, never re-purposed.
   414→7. **Frecency over recency.** Recent alone is volatile; frequency alone is stale. Frecency (frequency × recency decay) matches mental models (Raycast, Spotlight, Alfred).
   415→8. **No-modal-where-possible.** Linear does inline rename; Notion does inline `/`-commands. Modals interrupt flow. Reserve modals for destructive confirmations and complex forms.
   416→9. **Optimistic UI (Simon Hearne, UX Planet).** Show the final state *before* the async work completes; reconcile on success; rollback on failure. For LCKED: copying a password should show "Copied ✓ 30s" instantly, decrypt in the background.
   417→10. **The tool should disappear (Linear Method).** "Software project management tools should build with the end users – the creators – in mind. Keeping individuals productive is more important than generating perfect reports." → the UI fades; the task remains.
   418→11. **Native feel over web feel (Raycast).** No `cursor: pointer` on controls, no hover-everywhere, no flicker on transitions, popovers that extend beyond window bounds. The user should never think "this is a website."
   419→12. **Simple first, then powerful (Linear Method).** Ship a discoverable plain path first; layer keyboard power on top. "Do not introduce hidden power-user behavior before the plain path is already strong" (UX Patterns).
   420→13. **Decide and move on (Linear Method).** Opinionated defaults beat infinite configuration. Don't make the user design their own shortcut scheme from scratch.
   421→14. **Handoffs are deliberate (Solomon).** Decide explicitly where the palette ends and a form begins — don't improvise.
   422→
   423→### 7.2 The "seamless" checklist (synthesised)
   424→- [ ] Every keypress paints in <100 ms.
   425→- [ ] Every surface has `Esc`, `Enter`, and a forward action.
   426→- [ ] No state lost across modal/palette/lock transitions.
   427→- [ ] Active list item is preserved across re-renders.
   428→- [ ] Optimistic UI for all mutations (copy, edit, delete, lock).
   429→- [ ] No flicker on view transitions (pre-render, sync with rAF).
   430→- [ ] Reduced-motion users get the same information without motion.
   431→- [ ] Single-key shortcuts disabled in text inputs and remappable.
   432→- [ ] `?` cheat sheet, context-aware, accessible to screen readers.
   433→- [ ] `⌘K` palette with frecency ranking, favorites (`⌘1`–`⌘9`), and contextual actions.
   434→- [ ] Roving tabindex between list and detail; arrow keys route spatially.
   435→- [ ] Focus rings ≥2 px, ≥3:1 contrast, `:focus-visible` only.
   436→- [ ] ARIA live regions announce selection and result counts.
   437→- [ ] Scroll-into-view on every active-item change.

   532→## 10. Synthesised Principles (named, for LCKED's design doc)
   533→
   534→1. **The 100ms Rule** — every keystroke paints in <100 ms or the app is "keyboard-capable", not "keyboard-first" (Nielsen).
   535→2. **Spatial Consistency** — `j`/`k` always mean down/up; `Enter` always activates; `Esc` always closes the topmost surface. Never re-purpose (Linear, Superhuman, GitHub).
   536→3. **Frecency over Recency** — rank returning surfaces by frequency × recency decay; pin favorites above all (Raycast, Spotlight, Alfred).
   537→4. **No Dead-Ends** — every surface has `Esc`, `Enter`, and a forward action; leader keys show their options (Linear's `g`-hint).
   538→5. **Zero State-Loss** — modal/palette/lock transitions preserve scroll, active item, search, and unsaved drafts (UX Patterns).
   539→6. **One Palette, Mode Prefixes** — `⌘K` with `>`/`#`/`@` scopes scales better than many palettes (GitHub, Sublime).
   540→7. **Modifier-Tiered Verbs** — the same verb at modifier tiers (`⌘C`/`⇧⌘C`/`⌥⌘C`) compresses a password manager's most-used actions (1Password).
   541→8. **Quasimodes over Toggles** — hold-to-reveal is safer than toggle-and-forget (1Password, Raskin).
   542→9. **Contextual Actions** — `⌘K` on an item shows actions *for that item*; the palette is a verb, not just a navigator (Linear, Solomon).
   543→10. **Muscle-Memory Routes are Deterministic** — aliases/favorites never reorder; fuzzy is for discovery, not for the fast path (Raycast strict alias matching).
   544→11. **Native Feel over Web Feel** — no `cursor:pointer` on controls, no hover-everywhere, no flicker on transitions, popovers extend beyond bounds (Raycast).
   545→12. **Power-User ≠ Inaccessible** — single-key shortcuts off in inputs, remappable, with ARIA live regions announcing selection (WCAG 2.1.4, WAI Combobox).
   546→13. **Simple First, Then Powerful** — ship the visible path; layer keyboard power on top (Linear Method, UX Patterns).
   547→14. **The Tool Disappears** — optimise for the daily driver, not the occasional visitor; the UI fades and the task remains (Linear Method).
